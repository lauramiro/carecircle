## 1. AI Approach

### 1.1 Model Choice & Justification

CareCircle uses an LLM for the **Conversational AI Q&A** feature. The **Hospital Summary PDF** is generated without an LLM – it is a deterministic assembly of live data from Supabase. The **Weekly Insight Engine** also uses rule‑based pattern matching, not an LLM.

| Feature | Model / Approach | Rationale |
|---------|----------------|------------|
| **Conversational AI Q&A** | Llama 3.3‑70B (Groq LPU) | Interactive chat demands sub‑2s response. Groq LPU delivers < 800ms. Strong instruction‑following for grounding rules. |
| **Hospital Summary PDF** | Deterministic data assembly + PDF renderer (no LLM) | Patient data is sensitive; a template‑based PDF eliminates hallucination risk and ensures all 8 required sections are always present. |
| **Weekly Insight Engine** | Pattern matching (NestJS service) | Deterministic output required. No hallucination risk. < 100ms per patient. Zero API cost. Fully unit‑testable. |

**Why Llama 3.3‑70B over GPT‑4o or Claude for Q&A**  
Groq's LPU inference hardware was the decisive factor. GPT‑4o and Claude API latencies at peak hours range from 2–8 seconds for equivalent prompts. Llama 3.3‑70B on Groq consistently delivers sub‑1‑second responses in testing, making it the right choice for an interactive caregiver chat feature.

### 1.2 System Prompt Strategy

**AI Q&A (Llama 3.3‑70B)**
- System prompt is fixed and loaded once at service initialisation.
- Care profile JSON is injected as the final section of the system message – **not** in the user message – to prevent prompt injection attacks from overriding grounding instructions.
- Temperature: **0.3** – allows natural phrasing while suppressing creative elaboration.
- Max tokens: **800** – sufficient for thorough answers; low enough to prevent verbose hallucination.

**Hospital Summary PDF**
- No LLM is used. The backend (`HospitalSummaryService`) queries Supabase for:
  - Patient details, current medications, GP contacts, recent handover journal entries, flagged patterns, and appointments.
- The data is rendered directly into a PDF using a templated layout (`PDFGenerationService`).
- This guarantees **zero hallucination** – every piece of information is directly from the database.

### 1.3 Grounding Approach

The AI Q&A feature follows a strict grounding principle: the model may only use data explicitly present in the care profile injected into the prompt. This is enforced through:

- **Fresh data fetch on every request** – `ProfileService.getCareProfile()` performs a live Supabase query on every API call. There is no caching layer.
- **Explicit prohibition in the system prompt** – The prompt contains: *"Only use information from the care profile provided. Do not draw on general medical knowledge, suggest diagnoses, or add any information not present in the profile data."*
- **Explicit fallback instruction** – The prompt instructs the model to clearly state when information is not in the profile, rather than inferring or inventing a response.

The Hospital Summary PDF achieves grounding by construction – no generative model is involved.

### 1.4 Hallucination Mitigation Measures

| Measure | Applied To | Description |
|---------|------------|-------------|
| Grounding instruction in system prompt | AI Q&A | Model explicitly forbidden from generating content not present in the care profile. |
| Low temperature (0.3) | AI Q&A | Reduces model tendency to embellish or paraphrase creatively. |
| Fresh data fetch (no caching) | AI Q&A, Hospital Summary | Model (or data assembly) always operates on current database state. |
| No LLM for hospital summary | Hospital Summary | Entire PDF is assembled from deterministic queries – zero hallucination risk. |
| Mandatory medical disclaimer | AI Q&A, Hospital Summary | Every AI response and every page of the hospital summary PDF carries a disclaimer – injected at render time, not generated by the model. |
| No LLM for insight engine | Weekly Insights | The entire insight pipeline uses deterministic pattern matching. No model can hallucinate a medication adherence figure. |
| Structured JSON input | AI Q&A | Profile data injected as strongly‑typed JSON, reducing risk of misinterpretation. |

## 2. Testing Strategy

### 2.1 Automated Tests

All automated tests are executed in the GitHub Actions CI pipeline on every pull request targeting `main`. The pipeline runs: lint → unit tests → integration tests → build. A pull request cannot be merged if any stage fails.

#### Unit Tests

| Test Suite | Purpose | Test File | Dataset |
|------------|---------|-----------|---------|
| `ProfileService` – profile assembly | Verifies `getCareProfile()` correctly fetches medications, logs, journal entries, appointments, and wellbeing check-ins. | `profile.service.spec.ts` | 5 synthetic profiles (complete, missing sections) |
| `WeeklyInsightGenerationService` – all types | Verifies all 5 insight types generate correct cards with correct severity. | `weekly-insight-generation.service.spec.ts` | 10 synthetic weekly digests (all insights, no insights, each type in isolation, edge cases) |
| `WeeklyInsightGenerationService` – empty data | Verifies graceful handling when 7‑day window has no data. | `weekly-insight-generation.service.spec.ts` | Empty arrays for all three data sources |

#### Integration Tests

| Test | Purpose | File | Verification |
|------|---------|------|---------------|
| AI Q&A – no invented data | Runs generation against 3 known profiles; cross‑checks every named item in output against source profile. | `ai-qa.integration.spec.ts` | String matching between AI output and source profile JSON. |
| Hospital Summary – section completeness | Sends a real care profile through the assembly service and verifies all 8 PDF sections are present. | `hospital-summary.integration.spec.ts` | Checks `HospitalSummaryData` has non‑null values for all 8 required fields before PDF rendering. |

## Prompt Templates Directory

All AI prompt templates are versioned in `/prompts` in the repository. Each file includes inline comments explaining the prompt's purpose, variable placeholders, constraints, and model configuration decisions:

- `prompts/ai-qa-system-prompt.md` – Llama 3.3‑70B system prompt for the conversational Q&A feature.
- `prompts/hospital-summary-prompt.md` – (Reserved for future LLM use; currently the hospital summary uses deterministic data assembly.)
- `prompts/insight-digest-prompt.md` – Documents the architectural decision to use pattern matching instead of an LLM for the weekly insight engine.
